Report visibility linearizes at the successful PostgreSQL UoW commit. Report
metadata, source links, the success audit event and the artifact's committed
state participate in that transaction. `authorize_commit` executes after
payload and metadata preparation, while source and retention locks remain held,
immediately before the transaction can publish. Callback denial, exception,
cancellation, audit insertion failure or transaction failure rolls back the
report and success receipt together. A lost response after commit is resolved
by a new request that rechecks current authorization before returning the
stable report identity.

The shared source-lock order is lifecycle shared lock, workspace/environment
generation, exact revision admission lock, current source head, exact-source
retention applicability pointer, then current AccessPolicy pointer. Multi-source
report and read paths sort by source object and revision identity. Artifact row
locks follow canonical source/authority locks, so tombstone and authorized read
serialize without reversing the source lock order. The canonical applicability
writer uses row lock plus generation CAS. PostgreSQL barriers verify lifecycle,
policy activation, source-head replacement, retention replacement and opposite
input lock orders. Report publication uses the shared bounded retry policy
(three total attempts), recreates the UoW, and rechecks source, AccessPolicy,
retention, manifest and commit authorization. A PostgreSQL integration test
injects a translated deadlock at the commit boundary and verifies one committed
report/audit identity after a fresh authorized attempt. This does not prove
every writer participates in the canonical lock inventory or simulate a server
crash. External approval revocation requires #813's bounded fence/lease before
production composition.

## Evidence and limits

The vertical slice is split into focused PostgreSQL tests, including
`test_postgresql_private_asr_authorized_synthetic_report_commit`. They use an
isolated PostgreSQL service, current Alembic migrations, `spine_runtime`, real
canonical source/head and AccessPolicy records, the canonical retention
applicability repository, deterministic test-only approved terms, concrete
source locks, concrete storage, and canonical UoW audit persistence. It checks
authorized read, exact lineage and expiry, denial/exception/audit failure,
concurrent duplicate visibility, retention replacement and lifecycle fencing.
Separate tests publish a sanitized aggregate and verify that source revocation
hides its row. They do not prove current external privacy approval on later
aggregate reads or physical deletion of aggregate payloads.

The test-only terms authority is available solely through explicit test
composition. It cannot be registered by production wiring. A production
storage instance with missing approval/terms providers denies. The opaque
`profile_ref` is accepted only as a typed reference to an applicability kind;
the resolver then loads and verifies the canonical database binding. UUID
equality is not proof of policy authority.

The report manifest metadata migration is `20261231_99`, followed by
`20270101_100`, which persists the exact per-source retention disposition on
report artifacts. Reads and idempotent retries compare the entire current
disposition (policy and terms IDs/digests, generation, class, start event,
approval and cleanup/backup evidence) as well as derived expiry. This prevents
an equal-expiry but different terms version from authorizing a prior report.
These migrations add metadata to the existing tables; they do not create a
second registry. Frozen dataset versions and #661 thresholds are unchanged.
