# Private ASR restricted storage runbook

Status: implementation qualification only. Production qualification is
`NOT_VERIFIED` until an operator records evidence for a named environment.
Implementation and fixtures use synthetic identifiers and generated bytes;
they do not read recordings or run ASR inference.

## Topology and trust boundary

`PostgreSQLPrivateASRStorage` stores restricted payload bytes and manifests in
the existing Spine PostgreSQL database under the `spine` schema. Its runtime
role is subject to forced row-level security keyed by transaction-local
`spine.workspace_id`, `spine.environment_id` and `spine.purpose`; all four
private ASR tables use the fixed `asr_model_evaluation` purpose. The adapter also checks those
scope fields in every query and validates `TrustedPersistenceContext` through
the composition-root verifier. `PrivateReference` is an opaque identifier; it
does not grant access.

The adapter receives current authority readers for admission, AccessPolicy and
the approved private ASR retention profile. It verifies exact source object,
revision, digest, purpose, actor, scope, current policy, authority expiry and
retention profile before touching payload bytes. Reads first select metadata,
check authority and fences, and only then select the payload.

The storage classes are distinct: `staging` holds bounded incomplete/derived
bytes, `original` holds a verified immutable source copy, `annotation` holds
versioned private annotations, `report` holds detailed qualification reports,
canonical `audit_events` hold content-free audit receipts, and
`private_asr_aggregate_exports` holds only allowlisted sanitized aggregates.
No URL or repository path is produced.

## Transaction and publication

Report preparation inserts a `staging` row inside one PostgreSQL transaction.
The adapter verifies report schema, scope, digest, audit receipt, source
lineage, current AccessPolicy, current retention and source fences. It takes
transaction advisory locks for every exact revision and row locks for current
policy pointers and existing source-fence rows. It checks source-object scope
inside the transaction. It awaits `authorize_commit` after
preparation while those locks remain held, then changes the row to `committed`.
The payload, manifest identity and report receipt reference become visible at
the successful PostgreSQL transaction commit. That commit is the
linearization point. Callback refusal, exception or cancellation rolls back the
new row and report-source associations.

Storage-level source revocation takes the same per-revision advisory lock. If
revocation obtains the lock first, report commit sees the fence and fails. If
report commit obtains it first, the report commits before the revocation; the
revocation then tombstones source artifacts and linked reports in its own
transaction. Current AccessPolicy activation serializes on the same canonical
current-policy row. The current retention-profile reader and source-revision
head reader do not expose transaction-lock participation. Their independent
updates remain a contract gap for strict commit-time TOCTOU proof. The focused
PostgreSQL test substitutes a no-op for canonical source-row locking; it proves
storage transaction rollback, idempotency and scope behavior, but not
AccessPolicy lock privileges or external authority serialization. An external
authority that does not participate in the protocol remains outside the
guarantee and must not be represented as transactionally fenced.

## Data lifecycle and retry

Staging identities are deterministic for workspace, environment, exact source
revision and digest. A retry resumes an incomplete row. Finalization verifies
the whole byte string against the admitted revision's `original_sha256` and
length. The canonical `revision_digest` identifies revision metadata and is not
the audio-content digest. Append, finalization and revocation share a revision
advisory lock; revocation tombstones incomplete staging as well as committed
artifacts. Immutable source identity is deterministic for the exact revision
and verified digest. Annotation identity is stable for record/version. Report identity is stable for its
idempotency key; concurrent retries serialize on a PostgreSQL advisory lock.
After a lost response, replay rechecks authority and returns the committed
identity without creating another visible report.

Staging, report and annotation deletion uses tombstone state and clears payload
bytes within the database. Source revocation advances a durable fence epoch and
tombstones derivatives and linked reports. Retention expiry checks the stored
expiry copied from the exact current approved profile. Cleanup is idempotent.
The canonical audit writer retains only bounded operation/outcome metadata and
the exact source revision reference where supplied.

The database transaction covers rows in this database only. It does not prove
physical media erasure, WAL retention windows, replica deletion or backup
deletion. Operators must define backup retention, restore-time tombstone
reconciliation and expired-payload cleanup for every replica and backup set.

## Recovery and audit integrity

PostgreSQL rolls back an uncommitted report on process or connection loss. A
crash after commit but before the caller receives its response is recovered by
replaying the same idempotency key and verifying the committed digest. The
canonical audit receipt is written through Spine's existing PostgreSQL UoW
audit writer; the report references its immutable event id. Aggregate export
stores a separately sanitized object and its audit reference. Its release
callback runs inside the PostgreSQL insertion transaction, immediately before
audit and aggregate persistence. The callback's underlying privacy authority
does not provide a transaction lock, and the existing UoW audit writer commits
through a separate transaction; successful aggregate publication and its audit
event are not one atomic unit. This remains a contract gap, and aggregate export
is not qualified until both authorities can share a commit boundary.

## Operator deployment qualification checklist

For each named environment, record evidence for:

- PostgreSQL version, schema migration head, database/role identities and RLS
  settings; runtime must not use a bypass-RLS or migration role.
- Secretless connection configuration, network reachability, backup/replica
  topology, encryption-at-rest mechanism and key ownership.
- Composition wiring to current purpose authority, AccessPolicy, approved
  retention profile, canonical audit writer and trusted context verifier.
- Approved retention profile identity, expiry, revocation propagation and
  cleanup schedule; confirm profile changes reach the resolver.
- Concurrent commit/revocation and AccessPolicy activation using the same
  database and locking records as production.
- Restart recovery for interrupted staging, lost commit responses and cleanup;
  reconcile committed reports, audit references and tombstones.
- Backup/replica deletion and restore reconciliation, with evidence that expired
  and revoked payloads cannot be served after recovery.
- Restricted operator access, audit review, database log parameter redaction,
  monitoring without payload/source identifiers, and incident response.
- A synthetic canary only, followed by an independent security review. No real
  customer recording or ASR run is part of this ticket.
