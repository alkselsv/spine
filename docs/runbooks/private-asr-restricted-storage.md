# Private ASR restricted storage runbook

Status: implementation qualification only. Production qualification is
`NOT_VERIFIED` until exact authority and operator evidence exists for a named
environment. Implementation and fixtures use synthetic identifiers and
generated bytes. No customer recording or ASR inference is involved.

## Topology and trust boundary

`PostgreSQLPrivateASRStorage` stores staging, immutable originals, annotations
and detailed reports in the existing Spine PostgreSQL database under forced
RLS. Runtime transactions set workspace, environment and purpose; private ASR
operations require the `asr_model_evaluation` purpose and a verified
`TrustedPersistenceContext`. Opaque references are identifiers only. No public
URL or filesystem export is created. The adapter does not publish sanitized
aggregates; that path fails closed.

The adapter uses existing Spine source lifecycle/admission locks, current
source head and AccessPolicy storage, canonical `RetentionApplicability` and
canonical audit UoW. It does not create a second source registry, retention
registry, manifest authority or audit store. Report manifest lineage is
verified through a narrow port; the PostgreSQL acceptance test injects an
isolated synthetic verifier. No production verifier is registered by this
change.

## Retention authority and expiry

The production resolver is `PostgreSQLPrivateASRRetentionResolver`. It runs
inside the artifact transaction and locks the exact-source current
applicability pointer. It re-reads source/revision lineage and validates scope,
current applicability ID and generation, policy ID/version/digest, artifact
class membership, validity and the injected approval/terms evidence. It binds
the request's opaque profile reference to the loaded canonical applicability;
matching UUIDs alone do not authorize a request. Source-class applicability
is denied until shared locking for that pointer type is defined.

`ApprovedRetentionTermsProvider` supplies exact versioned rules, starting
event, duration, approval evidence, exception/hold state, and cleanup/backup
obligation references. The adapter derives `expires_at` deterministically from
the verified starting event and approved duration. Applicability
`effective_until` and processing-admission expiry are not artifact deadlines.
A legal hold does not authorize reads or publication. Expiry does not itself
authorize deletion. Missing, stale, ambiguous, revoked or unapproved evidence
denies. Report rows persist a sorted per-source disposition snapshot with the
exact policy/version/digest, applicability ID/generation, terms ID/version/
digest, artifact class, starting event/time, approval evidence and
deletion/backup obligation references. Reads and retries compare this whole
snapshot with the freshly resolved current authority, so a different terms
version cannot pass merely because it yields the same expiry timestamp.

The PostgreSQL positive test injects explicit deterministic synthetic terms
and approval evidence. This is a test-only composition and cannot be used as a
production fallback. Production policy terms and approval/revocation authority
are still missing; any external authority not coordinated with this database
transaction remains outside the proven revocation fence.

## Transaction and publication

For report publication, the transaction boundary includes the report row,
manifest and source-link metadata, artifact committed state, and canonical
successful publication audit event. `authorize_commit` runs after preparation
and verification, with canonical locks held, immediately before the report can
become visible. The successful PostgreSQL UoW commit is the linearization
point. Callback denial, exception, cancellation, audit insertion error or
transaction rollback leaves neither a visible report nor a successful
publication receipt.

The lock order is:

1. Source lifecycle shared lock.
2. Workspace/environment generation counter.
3. Exact SourceRevision admission lock.
4. Current source head.
5. Exact-source current retention applicability pointer.
6. Current AccessPolicy pointer.

Canonical retention updates use row lock and generation compare-and-swap.
The PostgreSQL integration test exercises report publication against source
lifecycle withdrawal and retention applicability replacement using barriers.
The full matrix for AccessPolicy activation/revocation, every canonical writer,
opposite transaction entry orders and deadlock handling remains incomplete.
An external approval authority is not atomically fenced unless its revocation
protocol participates in this database transaction or supplies an established
coordinated version fence.

Detailed report content is never part of aggregate output. Aggregate export
remains blocked until sanitized payload, small-cell/privacy checks, current
release authorization and canonical audit share a demonstrable visibility
boundary.

## Manifest and lineage

Before a report is committed, the verifier result must bind exact manifest
identity/digest/version, dataset identity, approved split, unique record
membership and exact SourceObject/SourceRevision/content digest. Storage checks
the binding again against persisted immutable originals and report outcomes.
The integration test uses only a synthetic manifest fixture. Production use
requires the authoritative #771/#772 admission resolver; caller-supplied
record/revision pairs are insufficient.

## Retry, cleanup and recovery

Report identity is stable for the idempotency key. Same-key same-payload retry
rechecks current source, AccessPolicy, retention and manifest eligibility
before returning the committed result. Same key with a different payload is a
conflict. Concurrent duplicate requests serialize and expose one report and
one success receipt. Uncommitted PostgreSQL work rolls back; a committed
report/audit pair survives a lost response and can be reconciled by a fresh
authorized retry.

These database behaviors are covered by synthetic integration tests. The test
does not constitute process-kill/restart, physical deletion or restore
qualification. Tombstones and cleanup are idempotent database state changes;
WAL, replicas, snapshots and backups may retain prior bytes. Operators must
define and verify backup/replica deletion and restore-time tombstone/receipt
reconciliation. Encryption-at-rest, physical erasure and production recovery
are `NOT_VERIFIED` absent named-environment evidence.

Retention expiration now has a synthetic authorized PostgreSQL path. It
re-resolves current applicability and approved terms inside the deletion UoW,
verifies exact persisted source/revision lineage and scope, checks the derived
deadline, obtains an action-specific deletion grant bound to the artifact-state
digest, appends minimal audit evidence, and tombstones/clears primary payload
visibility in the same transaction. Staging cleanup is restricted to exact
staging artifacts and also requires deletion authority. Missing authority, a
future deadline, wrong artifact type, mismatched profile, forged reference or
audit failure leaves the artifact unchanged. These fixture authorities are
test-only; production wiring remains denied until #812 exists. Clearing a
PostgreSQL payload and writing a tombstone do not prove physical erasure from
WAL, replicas or backups.

Private reads acquire canonical source/retention/AccessPolicy fences before
share-locking exact original/report artifact rows through payload selection.
Deletion acquires source and authority locks before its exclusive artifact row
lock, preserving source-lock order while serializing reads and tombstones.

## Operator qualification checklist

For each named environment, record:

- PostgreSQL version, applied migration head, RLS forced on all private tables,
  and runtime role verified non-superuser and non-BYPASSRLS.
- Least-privilege grants for source/head locks, current policy and retention
  reads, private artifact operations and canonical audit append.
- Composition roots for trusted-context verification, current admission,
  AccessPolicy, approved retention policy terms, revocation and authoritative
  manifest lineage.
- Lock ordering and race tests against the actual canonical source, policy and
  retention writers.
- Secret/network configuration, backup and replica topology, encryption
  mechanism and key ownership.
- Restart recovery, lost-response replay, tombstone reconciliation and
  retention cleanup across active storage, WAL, replicas and backups.
- Restricted operator access, redacted database logs, audit review and
  incident-response procedures.
- Independent security review and synthetic-only qualification evidence.

Do not process customer recordings or claim production readiness from the
synthetic integration suite.
